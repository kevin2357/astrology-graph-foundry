## Dataset Notes and Weighting

This read uses both the generated synastry dataset and the generated composite dataset. The SDK output confirms that the synastry pipeline used expanded natal semantic graphs for both people, each with 189 semantic graph objects, over 4,200 natal relationships, and 164 transit/synastry-capable targets. The relationship output includes 7,825 Kevin-to-Bre aspect records, 7,825 Bre-to-Kevin aspect records, 164 house overlays in each direction, a composite chart, composite aspects, relationship metrics, evidence claims, semantic operator hints, and report materials.

For interpretation, I am deliberately weighting the evidence in layers:

1. **Core planet/angle synastry** is weighted most heavily for human-readable relationship analysis. This includes Sun, Moon, Mercury, Venus, Mars, Jupiter, Saturn, Uranus, Neptune, Pluto, Nodes, ASC/DSC, MC/IC.
2. **House overlays** are weighted strongly because they describe where each person lands in the other person’s life field.
3. **Composite chart placements and aspects** are used to describe the relationship as its own third entity.
4. **Expanded semantic graph material**—harmonics, antiscia, contra-antiscia, lots, declination relationships, dignity states, and derived points—is treated as secondary/confirming evidence unless it repeats the same theme already visible in the core chart.
5. **Theme metrics** are useful as a diagnostic, but the raw scoring is currently inflated by the large number of expanded objects and relationship permutations. The ranking of themes is useful; the absolute scores should not be read as literal “strength percentages.”

This is important because the synastry package is currently enormous and includes a very wide relationship matrix. The richness is valuable, but for prose synthesis the reader needs hierarchy: otherwise harmonic and antiscia microcontacts can drown out the humanly obvious placements. In this report, expanded graph features support the interpretation, but they do not overrule the core synastry.

## Technical Review of the Synastry/Composite Pipeline

The generated output is impressive, but the 330 MB synastry file points to the next optimization target.

### What Looks Good

The pipeline is clearly using expanded natal semantic graphs rather than only core planet positions. Both natal packages have 189 graph objects, including planets, angles, lots, antiscia points, contra-antiscia points, harmonic points, declination positions, dignity states, calculated points, and sect state. The synastry package includes core aspects, expanded-object aspects, house overlays, composite data, theme tags, semantic operator hints, source/target natal relationship context, relationship metrics, and report materials. The composite package is compact and clean at under 1 MB.

The default transit output changes also appear to be working well. The screenshot/zip includes compact analysis and streaming-index files for transits, and those are far smaller than the previous full transit output pattern.

### What Should Be Tightened

The synastry file size is dominated by `natal_synastry`, especially the two 7,825-record directional aspect arrays. A serialized-size check shows `natal_synastry` alone accounts for roughly 164 MB uncompressed. The next largest section is `natal_graphs`, around 6.9 MB. The composite section is tiny by comparison.

The issue is not the number of aspects alone; it is repeated payload on each aspect. Each synastry aspect often embeds full semantic operator hints and full source/target natal relationship context. That context is useful, but repeated thousands of times it becomes extremely expensive.

The best fix mirrors what was just done for the transit streaming index:

1. **Add a synastry candidate/relationship registry.** Store each unique expanded synastry contact once.
2. **Add object registries for each natal graph.** Aspects should reference `source_object_id` and `target_object_id`, not repeat rich descriptions everywhere.
3. **Move operator hints to object/aspect-type registries.** Daily/contact rows should store operator hint refs or compact operator strings, not repeated dict arrays.
4. **Move natal relationship context to a `natal_context_registry`.** Each synastry contact can store refs like `source_context_refs` and `target_context_refs`.
5. **Create `synastry.analysis.json` by default.** This should include core planet/angle aspects, top expanded confirmations, top overlays, relationship metrics, evidence claims, and composite summary. It should be the report-consumer default.
6. **Keep full synastry as opt-in.** The full research package is valuable, but it should probably require `--out-full` or equivalent.
7. **Add a compact streaming/indexed relationship view if game consumers need it.** For example: lookup by source person, target person, object pair, theme, house, or relationship type.

### Logging Observation

The log shows many repeated “Transit targets extracted: 164” messages during synastry generation. That suggests synastry may be repeatedly extracting targets or rebuilding context in an inner loop rather than compiling once per natal graph and reusing the compiled structure. Even if runtime is tolerable, this is a smell. The synastry pipeline should probably use `GraphCompiler` directly for both natal graphs, then pass compiled targets/context into the aspect builder.

### Runtime and Serialization

The log indicates the Kevin→Bre synastry dataset completed at 20:36:40 and the command completed writing at 20:37:00. That means writing the 330 MB JSON took about 20 seconds. The reversed Bre→Kevin write took about 10 seconds. Compute time appears more significant than composite but still not unreasonable; output size and repeated context are the main issue.

### Recommended Next Patch

The next SDK patch should be “compact synastry outputs,” analogous to compact transit outputs:

- default `synastry --out foo.json` writes `foo.analysis.json` and perhaps `foo.index.json`;
- `--out-full foo.full.json` writes the full research matrix;
- full research matrix uses registries/refs to avoid repeated operator/context payloads;
- relationship metrics and report materials should be recalibrated so expanded harmonic/antiscia volume does not swamp core relationship themes;
- logs should show compiled graph reuse and progress through source/target pair generation.
