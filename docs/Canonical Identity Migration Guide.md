# Canonical Identity Migration Guide

## Who should migrate

Existing exploratory packages may continue using the deterministic
`natal:<slug(display name)>` fallback. Any system that persists readings, joins
artifacts, caches by chart, or permits display-name changes should regenerate or
rescope its Natal sources with a stable explicit `source_chart_id` before treating
AGF as a production dependency.

Choose a caller-owned identifier that is stable for the lifetime of the canonical
chart lineage. AGF treats it as opaque; it need not expose a product database ID.
Do not place display names, timestamps, filesystem paths, calculation hashes, or
projection-context IDs in this field.

## New generation

Pass `source_chart_id` with the birth inputs through `BirthData`, `natal.build`,
the `astro-package natal --source-chart-id` CLI option, or `tools/build_natal.py`.
Persist the exact identifier alongside the source artifact and include it in
downstream lineage checks. A later display-name edit may update descriptive
metadata without changing canonical IDs.

## Existing packages

Prefer regeneration from retained normalized birth inputs and pinned calculation
configuration. When an existing Natal package itself is the authoritative input,
use:

```python
from astrology_graph_foundry.canonical_graph import (
    rescope_natal_package_source_chart_id,
)

rescope_natal_package_source_chart_id(package, "tenant:chart:stable-id")
```

The operation validates the old package, synchronizes explicit carriers,
rebuilds graph-derived layers, and migrates exact references. Save the result as
a new immutable artifact; do not overwrite a source already referenced by a
delivered reading. Repeating the operation with the same identity is idempotent.

Do not edit `source_chart_id`, object IDs, relationship endpoints, evidence, or
indexes independently. Mixed explicit carriers fail closed. Changing an explicit
identity intentionally changes every chart-scoped ID and therefore requires new
downstream projections and lineage records.

## Compatibility and versioning

This contract begins with AGF package version 0.6.0 and semantic identity policy
`semantic_sensor_identity_v1.1.0`. The optional input is additive, and legacy
fallback packages remain readable, but identity behavior is important enough to
warrant a minor package-version increment. Canonical graph schema `1.3.0` remains
unchanged because its required topology did not change.

Composite and Davison packages newly generated by 0.6.x use
`relationship_chart_identity_v1.0.0`; their participant-derived identity may
differ from historical name-derived output. Re-project migrated or regenerated
sources rather than joining old and new derived artifacts by canonical ID.

AGF 0.6.0 identity behavior has been qualified against the exact SPC 0.10.0
wheel recorded in the canonical-identity sprint evidence. Immutable production
release hashes and runtime pins remain the responsibility of the subsequent
release-engineering sprint.
